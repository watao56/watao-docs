## 良い点

### 1. ブルーオーシャン
「構造化データの定期監視SaaS」は市場に存在しない。Google Rich Results Testは手動・1ページずつ。この隙間は明確。

### 2. 被害額が定量化できる
CTR 30%低下→月間検索流入X万クリック→損失Y万円。ROIが計算しやすい=セールスピッチが作りやすい。

### 3. RoboGuardとの補完性
RoboGuard（robots.txt/sitemap監視）+ SchemaLint（構造化データ監視）でSEO保全スイートが完成。バンドル販売の可能性。

### 4. ECサイトとの相性
EC事業者にとってProduct Schemaの星評価・価格表示は売上に直結。「リッチスニペットが消えてたら教えてくれるサービス」のWTPは高い。

### 5. SQS+Lambda並列の設計
大量ページのスキャンをキューで分散処理する設計は適切。ページ単位で独立実行できるため、障害の影響範囲が限定的。

## 懸念点と改善提案

### 1. SPA/SSRサイトの対応（中程度）
React/Next.js等のSPAはHTMLに直接JSON-LDが埋め込まれず、JavaScriptで動的生成されるケースがある。
→ **対策**: 基本はHTMLパース（cheerio）で高速処理。SPA検知時のみPuppeteer fallback。設計書に言及あり。

### 2. 構造化データの認知度（中程度）
「構造化データ」「JSON-LD」を知らないサイト運営者が多い。特に日本市場。
→ **対策**: 「リッチスニペット」「検索結果の星評価」というわかりやすい言葉でマーケ。「あなたのサイト、Google検索で星が出てますか？」のLP。

### 3. Schema.org仕様の更新追従（軽微）
Schema.orgは定期的に新プロパティを追加する。バリデーションルールの陳腐化リスク。
→ **対策**: schema-dtsパッケージの自動更新。必須プロパティのみチェック（推奨プロパティは警告レベル）。

### 4. Google Rich Results Testとの差別化
「Googleの無料ツールでいいのでは？」への明確な回答が必要。
→ **対策**: 「Googleのツールは1ページずつ手動。SchemaLintは100ページを毎日自動チェック。壊れたら即通知」。

# Python Quest - 設計書レビュー

> シニアエンジニアによる技術レビュー
> レビュー日: 2026-02-16

## 総合評価

**B+** — 教育コンセプトと段階的アプローチは秀逸。技術選定も堅実。ただし、子供向けサービスとしてのセキュリティ設計、テスト戦略、運用面の考慮が不足しており、このまま本番投入するには詰めが甘い箇所がある。

---

## 1. アーキテクチャ評価

### 👍 良い点

- **Skulptによるブラウザ内Python実行は最大の設計勝利。** サーバーサイド実行のセキュリティリスク（サンドボックスエスケープ、リソース枯渇）を根本的に排除している。コスト面でも正解。
- **Next.js + Supabase + Vercel** の組み合わせは2026年時点でも十分実績のあるスタック。個人〜小規模チーム開発に適している。
- **Blockly→Python変換がBlockly標準機能**という点を活かしている。車輪の再発明を避ける判断は正しい。
- **問題データをJSONで管理→後からDB移行**という段階的アプローチは、MVPとして正しい。

### ⚠️ 懸念点

- **Next.js API Routesにバックエンド全載せ**はMVPとしては問題ないが、先生用管理画面やクラス管理のビジネスロジックが増えた段階でAPI Routesの肥大化が予想される。ドメイン層の分離設計が言及されていない。
- **状態管理にZustandを選定**しているが、クエストの進捗状態・エディタ状態・ゲームUI状態など、管理する状態のスコープが整理されていない。Zustandは軽量だが、ストアの分割設計を事前に決めておかないとカオスになる。
- **リアルタイム機能の設計が不在。** Supabaseのリアルタイム機能に言及しつつ、具体的な利用シーンがない。先生が生徒の進捗をリアルタイムで見たいなら必要だし、不要なら言及しない方がいい。
- **キャッシュ戦略が未記載。** 問題データ（JSON）はSSGで静的生成できる。ユーザー進捗はSWRやReact Queryでキャッシュすべき。この辺の戦略がないと、無駄なAPIコールが発生する。
- **エラーハンドリング・リトライ戦略が未記載。** ネットワーク不安定な学校環境を想定すると、オフライン時のコード保存やリトライは重要。

## 2. セキュリティ

### 🚨 重大な懸念

- **COPPA/個人情報保護法への対応が一切記載されていない。** 子供向けサービスの設計書でこれが欠落しているのは致命的。日本では「青少年が安全に安心してインターネットを利用できる環境の整備等に関する法律」がある。13歳未満のユーザー登録には保護者の同意が法的に必要。
- **認証方式に「Google/メール認証」とあるが、小学生がGoogleアカウントを持っている前提は危険。** クラス単位で先生がアカウントを作成する「招待コード方式」の方が現実的。メールアドレス不要のログイン手段（ユーザーID + パスワード、またはQRコード）を検討すべき。
- **個人情報の最小化原則。** 子供の名前・メールアドレスをどこまで収集するか、保存期間は？プライバシーポリシーの策定が必要。

### ⚠️ その他

- **Skulptのサンドボックス安全性。** ブラウザ内実行なのでサーバーリスクはないが、`while True`の無限ループでブラウザがフリーズする問題への対策が必要。実行ステップ数の上限設定は必須。
- **XSS対策。** ユーザー入力（コード、名前）の表示時のサニタイズ。特にコードをそのまま表示する場面が多いため注意。
- **Supabase RLS（Row Level Security）の設計が未記載。** 他人の進捗データを閲覧・改ざんできないようにするRLSポリシーは最低限必要。
- **不正なXP/コイン操作の防止。** クライアントサイドでXPを加算してAPIに送る設計だと改ざん可能。サーバー側で正解判定→XP付与する設計にすべき。

## 3. UX/教育設計

### 👍 良い点

- **Scratch→変換→Python→turtleの4段階螺旋型カリキュラムは非常に優れている。** 同じ概念を異なるモードで繰り返す設計は、学習の転移を促進する。教育工学的にも理にかなっている。
- **ワールド2（変換の洞窟）のコンセプトが秀逸。** ブロック→テキストの「橋渡し」を明示的にカリキュラム化しているサービスは少ない。ここがこのプロダクトの最大の差別化ポイント。
- **RPG要素（称号・NPC・クエスト形式）は子供の動機づけに効果的。** 内発的動機と外発的動機のバランスが取れている。
- **★評価基準がシンプルで明快。** 子供にとって分かりやすい。
- **段階的ヒントシステム** は教育的に正しいスキャフォールディング。

### ⚠️ 改善すべき点

- **各ワールド8問は少なすぎる。** 特にワールド1と3は、1概念1問では定着しない。1概念につき最低2〜3問（基本・応用・チャレンジ）欲しい。ワールドあたり15〜20問が理想。
- **つまづいたときの救済設計が弱い。** ヒント3段階だけで解けなかった場合どうなるか？「答えを見る」「スキップして次へ」「別の練習問題をやる」などのフォールバックが必要。諦めて離脱するのが最悪のシナリオ。
- **フィードバックの質が「正解/不正解」だけ。** 不正解時に「何が違うのか」を具体的に示す仕組みが必要。期待出力と実際の出力のdiff表示、よくあるミスのパターンマッチ（例：`print`の括弧忘れ→「括弧を忘れていないかな？」）など。
- **ワールド3でいきなり関数（def）が登場するが、ワールド1にはない。** 螺旋型と言いつつ、ワールド3で新概念を追加している。ワールド1で「関数ブロック」を体験させるか、ワールド3の関数は別ワールドに分離すべき。
- **turtle（ワールド4）の正解判定「画像比較 or 座標比較」はどちらも難しい。** 画像比較は色や線の太さのわずかな差で不正解になりがち。座標比較はturtleの状態追跡が必要。具体的なアルゴリズムの検証が必要。
- **自由制作（4-7）の評価基準が不明。** 自由制作に★評価は不適切。「提出してXP獲得」の方が教育的に正しい。
- **連続ログインストリークは子供向けには慎重に。** プレッシャーになって逆効果になるケースがある。3日以上途切れてもペナルティなし、再開を褒める設計が望ましい。

## 4. 技術的リスク

### 🔴 高リスク

| リスク | 詳細 | 対策案 |
|--------|------|--------|
| **Skulptの制約** | Python 3の全機能をサポートしていない。f-string、walrus演算子、一部の標準ライブラリが未対応。カリキュラムで使う機能がSkulptで動くか全て検証が必要 | カリキュラム設計段階で全コードをSkulptで実行テストすること。代替としてPyodide（WASM版CPython）も検討 |
| **Skulptのturtleサポート** | Skulptのturtle実装は本家CPythonと挙動が異なる部分がある。色指定やアニメーション速度など | 早期にプロトタイプを作り、ワールド4の全クエストが動作するか検証 |
| **Blocklyのカスタマイズ量** | Blockly標準のPython生成は、教育向けに最適化されていない場合がある。ブロックのラベルを日本語化、利用可能ブロックの制限など、カスタマイズが予想以上に必要になる可能性 | Blocklyの日本語対応状況を事前調査。カスタムブロック定義の工数を見積もりに含める |
| **Monaco Editorのバンドルサイズ** | Monaco Editorは非常に重い（数MB）。初回ロードが遅く、低スペックPCで問題になる可能性。学校のPC環境は古いことが多い | monaco-editor/esm による部分インポート、Web Worker設定の最適化、遅延ロード |

### 🟡 中リスク

| リスク | 詳細 |
|--------|------|
| **ブラウザ互換性** | 学校のPCはChromebookかWindows。ブラウザバージョンが古い可能性。Blockly・Monaco・Skulptの最低動作環境の確認が必要 |
| **無限ループ対策** | 生徒が`while True`を書いた場合のブラウザフリーズ。Web Workerでの実行+タイムアウト設定が必須 |
| **レスポンシブ対応のPhase 3後回し** | タブレット利用を想定するなら、UIの基本設計段階からレスポンシブを意識すべき。後からの対応は手戻りが大きい |

## 5. コスト見積もり

### 👍 良い点

- **無料枠の活用を前提とした設計は現実的。** MVPを¥0で始められるのは大きな利点。
- **ブラウザ内実行によるサーバーコスト排除** は正しく評価されている。

### ⚠️ 見落とし・懸念

- **開発人件費が完全に欠落。** 最大のコストは人件費。個人開発ならゼロだが、4〜6週間×4フェーズの工数は16〜24週間（4〜6ヶ月）。1人での開発を前提としているのか、チーム開発なのかで大きく異なる。
- **テストデバイス費用。** 学校環境（Chromebook、Windows PC、タブレット）での動作確認用デバイスが必要。
- **素材制作費の過小見積もり。** NPCキャラクター5体+ワールドの背景+アイコン+エフェクト素材を絵文字だけで済ませるのは、教育プロダクトとしてのクオリティに直結する。子供向けは見た目の魅力が継続率に大きく影響する。最低でもキャラクターイラストには投資すべき。
- **Vercel Hobby プランは商用利用不可。** Vercelの利用規約上、Hobbyプランは個人の非商用利用限定。教育機関に提供する場合はProプラン（$20/月）が必要になる可能性が高い。
- **監視・ログ費用。** Sentry、LogRocket等のエラー監視ツールの費用が未計上。本番運用なら必須。

## 6. ロードマップ

### 👍 良い点

- **MVPの範囲が適切。** ワールド1 + 基本機能に絞っている。ここで動くものを見せて検証するのは正しい。
- **認証をPhase 2に後回し（MVPはlocalStorage）** は賢い判断。

### ⚠️ 懸念

- **Phase 1が4〜6週間は楽観的。** Blockly統合とSkulpt統合だけで2〜3週間かかる可能性がある。特にBlocklyのカスタマイズ（日本語化、利用ブロック制限、Python生成のカスタマイズ）は想像以上に時間がかかる。**Phase 1は6〜8週間が現実的。**
- **Phase 2にコア機能を詰め込みすぎ。** 認証 + ワールド2 + ワールド3 + XP/レベル + 実績 + ★評価 を4〜6週間は無理がある。ワールド2と3だけで1フェーズ使うべき。
- **「全クエスト作成（32問）」がPhase 3にある**が、問題設計・テスト・難易度調整は想像以上に時間がかかる。コンテンツ制作専任が必要なレベル。エンジニアが片手間にやると質が落ちる。
- **ユーザーテスト（実際の子供に使ってもらう）のタイミングが未記載。** Phase 1完了後に即座にテストすべき。子供のUXは大人の想像と大きく異なる。
- **Phase 4の優先順位が不明確。** BGM、キャラカスタマイズ、ランキング、PWAが並列だが、ユーザーテストの結果に基づいて優先順位を決めるべき。

## 7. 改善提案

### 7.1 認証設計の見直し（優先度：高）

```
現在: Google/メール認証
提案: 招待コード + ユーザーID/パスワード方式を主軸に

フロー:
1. 先生がクラスを作成 → 招待コード発行
2. 生徒は招待コード + ニックネーム + パスワードで登録
3. メールアドレス不要（子供の個人情報最小化）
4. 先生がパスワードリセット可能
5. オプションでGoogleログイン連携（中学生向け）
```

### 7.2 Skulpt → Pyodide の検討（優先度：中）

SkulptはPython 2時代から存在する軽量な実装だが、Python 3の対応が不完全。**Pyodide（CPython の WebAssembly ビルド）** は重いが、完全なPython 3互換性がある。

- Pyodideの初回ロードは約10MB → キャッシュで2回目以降は高速
- turtle対応にはカスタムCanvas連携が必要（Skulptと同程度の工数）
- 将来的にNumPy等のライブラリ対応も可能

**提案:** MVP はSkulptで進め、制約にぶつかったらPyodideに移行できるよう、Python実行層を抽象化しておく。

```typescript
interface PythonRunner {
  execute(code: string): Promise<ExecutionResult>;
  setStdout(callback: (text: string) => void): void;
  setCanvas(canvas: HTMLCanvasElement): void;
}

// 実装を差し替え可能に
class SkulptRunner implements PythonRunner { ... }
class PyodideRunner implements PythonRunner { ... }
```

### 7.3 つまづき救済システム（優先度：高）

```
ヒント1 → ヒント2 → ヒント3 → ?

追加すべきフォールバック:
- 「答えを見る」ボタン（★0扱い、XP半減）
- 「似た練習問題をやる」（同じ概念の別問題へ誘導）
- 「パイソン先生に聞く」（将来的にLLMで個別指導）
- 一定時間操作なし → NPCが「大丈夫？」と声かけ
```

### 7.4 エラーメッセージの日本語化（優先度：高）

Skulpt/Pythonのエラーメッセージは英語。子供には理解不能。

```
SyntaxError: unexpected EOF while parsing
→ 「コードが途中で終わっているよ！括弧や:を忘れていないかな？」

NameError: name 'pritn' is not defined
→ 「"pritn" って何だろう？もしかして "print" の間違いかな？」

IndentationError: expected an indented block
→ 「if文の中身は、スペース4つ分右にずらしてね！」
```

よくあるエラーパターン10〜20個をマッピングするだけで体験が劇的に改善する。

### 7.5 問題数の拡充とレベルデザイン（優先度：中）

```
現在: 各ワールド8問（ボス含む）= 計32問
提案: 各ワールド15〜20問 = 計60〜80問

構成例（1概念あたり）:
- 基本問題: ガイド付き、ほぼ確実にクリアできる
- 練習問題: 少しアレンジ、自力で解く
- チャレンジ問題: 応用、★3を狙う上級者向け（任意）

これにより:
- 全問クリアの達成感が増す
- つまづいた概念を反復できる
- 上級者は退屈しない
```

### 7.6 アクセシビリティ（優先度：中）

設計書にアクセシビリティへの言及がゼロ。教育プラットフォームとして最低限：

- キーボードナビゲーション対応
- 色覚多様性への配慮（色だけで情報を伝えない）
- フォントサイズの調整機能
- スクリーンリーダー対応（特にコンソール出力部分）

### 7.7 分析基盤（優先度：中）

どのクエストで離脱が多いか、どのエラーが頻発するか等のデータ収集設計がない。

```
追跡すべきイベント:
- クエスト開始/クリア/離脱
- ヒント使用（どの段階で）
- エラー発生（種類と頻度）
- 実行回数
- 滞在時間
- ワールド間の遷移パターン
```

これらは問題改善・カリキュラム調整に不可欠。Supabaseに保存してダッシュボードで可視化できるようにすべき。

## 8. 総括

### この設計書の最大の強み

1. **Scratch→変換→Pythonの段階的アプローチ**は教育設計として非常に優れている。特に「変換の洞窟」というブリッジ段階を明示的に設けている点は、他の類似サービスにない差別化ポイント。
2. **ブラウザ内Python実行**による、サーバーコスト・セキュリティリスクの排除は正しいアーキテクチャ判断。
3. **RPG/ゲーミフィケーション要素**のバランスが良い。過剰でもなく、不足でもない。

### この設計書に足りないもの

1. **子供の個人情報保護に関する法的・倫理的配慮**（最重要）
2. **エラーハンドリング・つまづき救済の設計**（UXに直結）
3. **テスト戦略とユーザーテスト計画**
4. **運用・監視・分析の設計**
5. **アクセシビリティへの配慮**
6. **人件費を含む現実的なコスト見積もり**

### 次のアクション推奨

1. ✅ Skulptでワールド1〜4の全概念が動作するか、2日以内にプロトタイプ検証
2. ✅ 子供の個人情報保護方針を策定し、認証設計を見直す
3. ✅ Blocklyの日本語化・カスタマイズの技術検証（1週間）
4. ✅ Phase 1のスコープを再定義（Blockly + Skulpt統合 + 3問で十分）
5. ✅ 可能な限り早い段階で実際の子供（2〜3人）にプロトタイプを触らせる

---

> **最終コメント:** 設計の方向性は正しい。「完璧な設計書を作る」より「動くものを子供に触らせる」フェーズに早く移行すべき。特にBlockly + Skulptの技術検証と、子供のUXテストが最優先。設計書の完成度を上げるより、プロトタイプを作って仮説を検証することを推奨する。

## 2. アーキテクチャ

### 👍 良い点

- **PythonRunnerインターフェース（§5.5）は優れた設計。** `execute`, `setStdout`, `setStderr`, `setCanvas`, `terminate` の5メソッドで実行層の関心事を適切に抽象化している。`ExecutionResult`に`turtleSteps`と`executionTimeMs`を含めているのも良い判断。
- **Zustandの5ストア分割（§5.7）は妥当。** Game/Progress/Editor/UI/Authの分離は適切。ただし後述の懸念あり。
- **キャッシュ戦略（§5.8）が明確。** 問題データSSG、進捗SWR、ランキング60秒キャッシュの粒度設計は適切。
- **オフライン対策（§5.10）** IndexedDB自動保存+オンライン復帰時同期は、学校環境を考慮した現実的な設計。

### ⚠️ 懸念点

1. **PythonRunnerのサーバー側実装が未設計。** §8.4でサーバー側正解判定を謳っているが、サーバー側でPythonコードをどう実行するかの設計がない。Next.js API Routes内でSkulptを実行する？Node.jsのchild_processでPythonを実行する？**これはアーキテクチャ上の重大な未決定事項。**

   - 案A: サーバーでもSkulptをNode.js上で実行 → Skulptがブラウザ向け設計なのでNode.js互換性に不安
   - 案B: 期待出力のみDB保存し、サーバーは出力文字列の比較のみ → コード自体の検証はクライアント側に依存、改ざんリスク残存
   - 案C: Docker/Firejailでサンドボックス実行 → インフラコスト増、Vercelでは不可

   **推奨:** 案Bの改良版。クライアントで実行→出力をサーバーに送信→サーバーは期待出力と比較+コードの基本的な整合性チェック（空コードでないか、期待するキーワードを含むか等）。完全な改ざん防止は諦め、「カジュアルな不正を防ぐ」レベルで十分。教育プラットフォームでは100%の改ざん防止よりUXが優先。

2. **Zustandストア間の依存関係が未整理。** クエストクリア時に`EditorStore`→`ProgressStore`→`GameStore`（XP加算）→`UIStore`（クリアモーダル）と連鎖的に状態が変わるが、この連鎖をどう管理するか（アクション内で他ストアを参照？ミドルウェア？イベントバス？）が未設計。

3. **SWR vs React Query の選定が未決。** §5.1に「SWR or React Query」と併記されているが、先生ダッシュボードのリアルタイム更新を考えるとReact Queryのほうが機能的に適している。決めておくべき。

## 3. セキュリティ

### 👍 大幅改善

- **認証フロー（§8.1）は子供向けサービスとして適切。** 招待コード+ニックネーム+パスワード、メールアドレス不要、先生経由のみ登録可能という設計は、COPPA/個人情報保護の観点で正しい。
- **RLS（§8.3）のSQLポリシーが具体的。** 自分の進捗のみ閲覧、先生は自クラスの生徒のみ閲覧、という設計は適切。
- **XP改ざん防止（§8.4）** サーバー側判定・付与の原則が明確。
- **XSS・CSRF・レート制限（§8.5）** 基本的な対策が網羅されている。

### ⚠️ 残課題

1. **招待コードの総当たり攻撃対策が未記載。** 8桁英数字の招待コードは`36^8 ≈ 2.8兆通り`で十分なエントロピーだが、APIレベルで招待コード入力の試行回数制限（例：同一IPから10回/時間）を設けるべき。

2. **パスワードの複雑性要件が未定義。** 子供向けなので複雑にしすぎると使えないが、最低限「4文字以上」等の要件は決めるべき。先生がリセットできる設計は良いが、初期パスワードの自動生成（先生が配布）も選択肢として検討を。

3. **セッション管理の詳細が未記載。** Supabase Authのセッション有効期限、リフレッシュトークンの扱い、学校の共有PCでのセッション残存リスク（前の生徒のセッションが残る問題）への対策が必要。**ブラウザを閉じたらセッション切れる設計が望ましい。**

4. **サーバー側Python実行の設計不在（前述）。** §8.4の「サーバー側で正解判定を実行（ブラウザ側のSkulpt実行とは別に検証）」と書いているが、具体的な実行方法が未設計。

## 4. UX/教育設計

### 👍 大幅改善

- **問題数67問は適切な量。** 1概念3段階（基本・練習・チャレンジ）の構成は教育工学的に正しい。反復と応用のバランスが良い。
- **つまづき救済システム（§3.6）は秀逸。** ヒント3段階→「答えを見る」/「似た練習問題」/「NPCアドバイス」の分岐は、離脱を防ぐ重要な仕組み。★0扱い（XP半減）で「答えを見る」のペナルティバランスも適切。
- **エラー日本語化（§9）が充実。** 10パターン以上のマッピング+コードのパターンマッチ（`pritn`→`print`の提案等）は、子供のUXを大きく改善する。
- **NPCの声かけ（3分操作なし→「大丈夫？」）** は離脱防止に効果的。
- **連続ログインのペナルティなし+再開褒めメッセージ** は子供向けとして正しい設計。

### ⚠️ 改善点

1. **ワールド2の問題形式バリエーションが不明確。** §2.3末尾に「穴埋め」「ブロック組み」「マッチング」と形式例があるが、16問中どれがどの形式かが未定義。変換モードの問題形式は実装に直結するため、もう少し具体化すべき。

2. **「似た練習問題をやる」の問題プールが不足する可能性。** §6.1のQuestテーブルに`related_quest_id`があるが、1対1の紐付け。つまづきが多い概念（条件分岐、ループ等）には複数の類似問題プールが欲しい。`related_quest_ids[]`（配列）にすべき。

3. **turtle（W4）の正解判定の「±5%許容」は曖昧。** `forward(100)`に対して`forward(95)`〜`forward(105)`がOKということだが、子供の入力ミスで`forward(10)`と書いた場合（桁数ミス）は弾くべき。**許容範囲は「±5%かつ±10以内」のような複合条件が望ましい。**

4. **ボスクエストの不合格時フローが未設計。** ボスクエストで不正解の場合、通常クエストと同じ救済フロー？ボスは「答えを見る」不可にして、前のクエストに戻す設計もあり得る。ボス戦の特別感と挫折回避のバランスを検討すべき。

5. **エラー日本語化のカバレッジ目標が不明。** §9.1に10パターン程度の例があるが、実際にSkulptが出すエラーの種類は数十種。Phase 1で10パターン→Phase 3で30パターン、のようなカバレッジ目標があると良い。

## 7. 新たに気づいた問題点

改訂によって新たに生まれた懸念を挙げる。

### 7.1 サーバー側Python実行の矛盾

§8.4で「サーバー側で正解判定を実行（ブラウザ側のSkulpt実行とは別に検証）」と明記しているが、§5.5のPythonRunnerインターフェースはブラウザ向け設計（`setCanvas`メソッド等）。サーバー側でのPython実行方法が未設計のまま、改ざん防止の要件だけが先行している。**実装時に最も困る箇所になる可能性が高い。** 前述の通り、現実的には「出力文字列の比較+基本的なコード整合性チェック」で十分。

### 7.2 設計書の肥大化

前回指摘を網羅的に反映した結果、設計書が非常に長くなった。これは悪いことではないが、**実装時に「どこに何が書いてあるか」を探すのが困難になる。** 目次の追加、または設計書を複数ファイルに分割（アーキテクチャ編、カリキュラム編、セキュリティ編等）することを推奨。

### 7.3 問題数67問の品質管理

32問→67問に拡充されたが、67問すべてを高品質に設計・テスト・難易度調整するのは想像以上に大変。特に「基本・練習・チャレンジ」の難易度差が適切かどうかは、実際の子供にテストしないとわからない。**問題のバージョニング（改訂時に別問題として管理）の仕組みも必要になる。**

### 7.4 オフライン時の進捗同期コンフリクト

§5.10のオフライン対策で「オンライン復帰時に自動同期」とあるが、2つのデバイスでオフライン状態でプレイした場合の進捗コンフリクト解決が未設計。教育現場では「学校のPCで途中まで→自宅のPCで続き」というシナリオがあり得る。**last-write-wins（最終更新優先）でよいが、XPの巻き戻りが起きないよう「XPは常に最大値を採用」のルールが必要。**

### 7.5 AnalyticsEventの肥大化

§10.1で11種のイベントを追跡するが、`code_execute`イベントは1クエストで何十回も発生し得る。50人×67問×平均10回実行 = 33,500イベント/周回。分析データの保存期間・アーカイブ戦略が未設計。Supabase Freeプランの500MB上限にも影響する。

## 9. 総括

改訂版は前回の指摘を**誠実かつ網羅的に反映**しており、設計書としての完成度は大幅に向上した。特にセキュリティ設計（認証フロー、RLS、XP改ざん防止）は前回の最大の弱点だったが、今回は実用的なレベルに到達している。

残課題はあるが、いずれも実装フェーズで解決可能なレベル。**この設計書をベースに実装を開始して問題ない。** 前回のレビューで「完璧な設計書を作るより動くものを子供に触らせるフェーズに移行すべき」と述べたが、その助言は今回も変わらない。
